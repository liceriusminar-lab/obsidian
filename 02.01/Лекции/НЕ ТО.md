### 1. Проектирование: общее и детальное

**Проектирование**: определение архитектуры, компонентов, интерфейсов и данных системы по требованиям. Это мост между «что делать» (спецификация) и «как делать» (код).

- **Общее (внешнее)**: крупные части системы (слои, подсистемы, интерфейсы между ними), модель данных, выбор СУБД и технологий, ограничения и риски.
- **Детальное (внутреннее)**: устройство каждого компонента (классы, алгоритмы, структуры данных, сигнатуры функций, схема БД, форматы данных и протоколы).

**Результаты этапа:**

1. Документ архитектуры (стиль, компоненты, решения с обоснованием).
2. UML-диаграммы: use case, activity, class, sequence.
3. Схема БД (ER-модель, нормализованные таблицы).
4. Спецификации интерфейсов модулей и API.
5. Технологические решения (язык, фреймворк, СУБД) с обоснованием.

### 2. Архитектура ПО и роль архитектора

**Архитектура ПО**: фундаментальная организация системы (компоненты, их связи, принципы развития). Это самые дорогие в изменении решения, поэтому их фиксируют рано и документируют.

**Архитектор:**

- принимает и обосновывает решения;
- следит за нефункциональными требованиями (производительность, надёжность, безопасность);
- удерживает целостность конструкции при доработках.

В учебной команде роль по очереди выполняет один из студентов. Он согласовывает структуру модулей и схему БД до начала кодирования.

### 3. Архитектурные стили

**Архитектурный стиль**: устойчивый способ организации системы из типовых частей и связей.

#### 3.1 Слоистая (n-tier)

Слои сверху вниз: **представление (UI) → бизнес-логика → доступ к данным (DAO/ORM, SQL) → БД**.

- Правило: слой использует только нижележащий, зависимости направлены вниз.
- Плюсы: понятность, слой можно заменить без переписывания других, удобное разделение работ.
- Минус: лишние уровни косвенности замедляют простые операции.

#### 3.2 Клиент-серверная

Сервер хранит данные и выполняет основную логику, клиенты запрашивают услуги.

- **Двухзвенная**: клиент — сервер БД.
- **Трёхзвенная**: клиент — сервер приложений — сервер БД.
- Пример: браузерный клиент (HTML/JS) + сервер с REST API.

#### 3.3 Монолит и микросервисы

|Критерий|Монолит|Микросервисы|
|---|---|---|
|Структура|Одно приложение, один процесс|Много мелких независимых сервисов|
|Разработка|Простой старт|Сложнее: сеть, контракты API, версии|
|Развёртывание|Любой релиз = выкладка всего|Каждый сервис отдельно|
|Масштабирование|Вся система целиком|Точечно, только нагруженный сервис|
|Отказоустойчивость|Сбой части может уронить всё|Отказ изолируется в одном сервисе|
|Команда|1–2 разработчика|Несколько автономных команд|
|Технологии|Единый стек|Свой стек у каждого сервиса|

**Вывод:** микросервисы оправданы при больших нагрузках и крупных командах. Для учебного проекта разумнее **модульный монолит** (единое приложение с чётко выделенными модулями по слоям).

#### 3.4 Модульная организация

**Модуль**: логически завершённая единица с известным интерфейсом (класс, пакет, сервис). Каждый модуль можно разрабатывать, тестировать и заменять независимо.

### 4. Связность и зацепление; SOLID

- **Связность (cohesion)**: единство ответственности внутри модуля. Нужна **высокая** (модуль делает одну работу). Плохой пример: класс `Utils`, куда свалено всё.
- **Зацепление (coupling)**: взаимозависимость модулей. Нужно **низкое** (общение через узкие интерфейсы). Плохо, когда изменение одного модуля ломает десять других.

**SOLID:**

|Буква|Принцип|Суть|
|---|---|---|
|S|Single Responsibility|У класса одна ответственность и одна причина для изменения|
|O|Open/Closed|Открыт для расширения, закрыт для изменения кода|
|L|Liskov Substitution|Подтип можно использовать вместо базового типа без сюрпризов|
|I|Interface Segregation|Много узких интерфейсов лучше одного «толстого»|
|D|Dependency Inversion|Зависеть от абстракций, а не от конкретных реализаций|

### 5. Паттерны проектирования и MVC

**Паттерн**: типовое проверенное решение повторяющейся задачи проектирования. Каталог GoF («банда четырёх») делит паттерны на **порождающие, структурные, поведенческие**.

|Паттерн|Тип|Суть|Пример|
|---|---|---|---|
|Singleton|порождающий|Один экземпляр класса и глобальная точка доступа|Подключение к БД, конфигурация|
|Factory Method|порождающий|Интерфейс создания объекта, конкретный класс выбирают наследники|Обработчики заявок: сервис, гарантия, возврат|
|Observer|поведенческий|Объект уведомляет подписчиков об изменениях|Смена статуса заявки: уведомляются клиент и мастер|
|Strategy|поведенческий|Взаимозаменяемые алгоритмы за общим интерфейсом|Скидка: фиксированная, процентная, накопительная|

**MVC (Model-View-Controller)**: архитектурный паттерн, разделяющий данные, представление и управление.

- **Модель**: данные и бизнес-логика.
- **Представление (View)**: отображает данные пользователю.
- **Контроллер**: принимает ввод, управляет моделью и представлением.

На нём основаны Django, Spring MVC и большинство веб-фреймворков. Пример («Библиотечный сервис»): каталог книг — модель, страницы каталога — представление, обработчики запросов — контроллеры.![[Pasted image 20261002102237.png]]

### 6. Проектирование данных

**ER-модель (сущность — связь)**: сущности, их атрибуты и связи (1:1, 1:N, M:N). Нужны первичные и внешние ключи.

Пример «Учёт заказов кофейни»: сущности Клиент, Заказ, Позиция заказа, Напиток. Связи (все 1:M): Клиент делает Заказы, Заказ содержит Позиции, Напиток входит в Позиции.

**Нормализация** устраняет избыточность и аномалии обновления:

- **1НФ**: все атрибуты атомарны (не «телефоны: дом, раб», а отдельные строки).
- **2НФ**: 1НФ + каждый неключевой атрибут зависит от **всего** составного ключа (цена позиции зависит от позиции заказа, а не только от заказа).
- **3НФ**: 2НФ + неключевые атрибуты не зависят от других неключевых (адрес кофейни хранится в таблице Кофейня, а не в каждом заказе).

Для учебного проекта достаточно 3НФ. Денормализация допустима осознанно (ради производительности) и фиксируется в документе архитектуры.

### 7. UML

**UML (Unified Modeling Language)**: стандартный графический язык моделирования ПО.

- **Структурные (статика):** классов, компонентов, развёртывания.
- **Поведенческие (динамика):** вариантов использования, деятельности, последовательности, состояний.

#### 7.1 Use case (варианты использования)

Показывает функции системы глазами пользователя.

- **Элементы:** акторы (человечки), варианты использования (овалы), граница системы (прямоугольник), связи.
- **Как строить:** определить акторов → перечислить цели каждого как варианты использования → связать; при необходимости добавить `extend` (расширение, необязательный сценарий) и `include` (включение, общий сценарий).
- **Пример** («Трекер задач»): Участник — «Создать задачу», «Переместить задачу»; Руководитель — «Назначить исполнителя» (include «Уведомить участника»).

#### 7.2 Activity (деятельность)

Блок-схема процесса.

- **Элементы:** старт (закрашенный круг), действия (скруглённые прямоугольники), переходы (стрелки), ветвления (ромб), параллельные потоки (жирные полосы синхронизации), финал; дорожки (swimlanes) показывают, кто выполняет действие.
- **Как строить:** выбрать процесс (оформление заказа) → перечислить шаги → найти ветвления (оплата наличными или картой) → при параллельных работах добавить полосы.

#### 7.3 Class (классов)

Основной результат детального проектирования.

- **Класс:** прямоугольник из 3 секций: имя / атрибуты / операции.
- **Видимость:** `+` публичная, `-` приватная, `#` защищённая.
- **Связи:**
    - ассоциация: линия;
    - агрегация: пустой ромб;
    - композиция: закрашенный ромб;
    - наследование: треугольник у родителя;
    - зависимость: пунктир.
- **Как строить:** существительные из требований → классы; глаголы → операции; указать множественности (1, 0..*, 1..*).
- **Пример:** Заказ (id, дата, статус, сумма; пересчитать(), изменитьСтатус()) ↔ Клиент; Заказ — ПозицияЗаказа (товар, количество), агрегация, 1..*.

#### 7.4 Sequence (последовательности)

Обмен сообщениями между объектами **во времени**; хороша для одного сценария от начала до конца.

- **Элементы:** линии жизни (вертикальные пунктиры), полосы активации (узкие прямоугольники), сообщения (стрелки сверху вниз; синхронное — закрашенная стрелка, ответ — пунктирная).
- **Как строить:** взять один сценарий use case → участники слева направо (пользователь, контроллер, сервис, БД) → сообщения по порядку.
- **Пример** («Бронь в музее»):  
    Пользователь → Контроллер: запрос брони  
    Контроллер → Сервис: `создатьБронь()`  
    Сервис → БД: INSERT  
    БД → Сервис: ok  
    Сервис → Пользователь: подтверждение

### 8. Инструменты проектирования

|Инструмент|Тип|Особенности|
|---|---|---|
|draw.io (diagrams.net)|Векторный редактор|Бесплатный, в браузере и офлайн, есть UML-палитра|
|PlantUML|Диаграммы кодом (текст → диаграмма)|Хранится в Git, легко версионировать|
|StarUML|UML CASE|Полная поддержка UML 2, генерация заготовок кода|
|Enterprise Architect|Промышленный CASE|Репозиторий моделей, трассировка требований, командная работа|

Для команды лучше draw.io (скорость) и PlantUML (диаграммы лежат рядом с кодом, их можно ревьюить в pull request).

### Связь с ПР5

В ПР5 команда строит для своего проекта 4 диаграммы:

1. уточнённую use case (по итогам ПР4);
2. activity для одного бизнес-процесса;
3. class по своей модели данных;
4. sequence для главного сценария.

Дополнительно фиксируются решение по архитектуре (слои, монолит) и схема БД в 3НФ. Диаграммы входят обязательным приложением в отчёт к дифзачёту. Для ПР5 use case и activity строятся в draw.io, экспорт в PNG.
